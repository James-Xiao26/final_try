# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

EdgeBoard (deployed as **WhaleWatcher**, getwhalewatcher.me) ranks Polymarket traders by a 0–10 "Skill Score" that is purely statistical forecasting edge — how reliably a trader's entry prices beat the market's eventual resolution, Bayesian-shrunk for sample size — rather than raw PnL. Beyond the leaderboard it also serves a **Markets** page, a **recent-trades activity feed** with a **Convergence** ("crowded markets") sub-section (markets the most leaderboard wallets hold, with a per-market detail page), and per-wallet **detail** (open positions, closed positions with P/L, a mark-to-market equity curve). A pnpm monorepo with two workspaces:

- `scripts/` (`edgeboard-scripts`) — TypeScript ingestion pipeline run via `tsx`. Pulls Polymarket's public APIs (Data + Gamma + CLOB), computes metrics, writes to Supabase.
- `web/` (`edgeboard-web`) — Next.js 14 App Router frontend that reads pre-computed data from Supabase and never computes metrics. It is read-only against Polymarket: the **one** exception is the Market Analytics page's live-enrichment fallback (`web/lib/polymarketLive.ts`), which fetches a market's snapshot/price series straight from Gamma+CLOB when the batch caches don't cover it (see Architecture).
- `supabase/migrations/` — the Postgres schema (18 migrations as of writing).

## Commands

Run from the repo root unless noted:

```bash
pnpm install
pnpm dev          # next dev (web), http://localhost:3000
pnpm build        # next build (web)
pnpm typecheck    # tsc --noEmit across BOTH workspaces (recursive)
pnpm ingest       # run the FULL ingestion pipeline (scripts/ingest.ts via tsx)
pnpm ingest:feed  # partial: refresh only the activity feed for current leaderboard wallets (--feed-only)
pnpm ingest:markets  # partial: refresh only the Markets table (--markets-only)
pnpm ingest:rescore  # partial: re-score the top RESCORE_TOP_N wallets/horizon and rebuild the leaderboard (--rescore-top)

pnpm --filter edgeboard-scripts test   # run the scripts unit tests (from repo root)
pnpm --filter edgeboard-web test       # run the web unit tests (pure lib/ logic)
pnpm --filter edgeboard-scripts probe  # probeClosedPositions.ts — ad-hoc inspect of the /closed-positions shape
```

The ingest CLI flags (`--feed-only`, `--markets-only`, `--rescore-top`) let the scheduler run cheap partial refreshes between full passes. Root `engines.node` is `24.x`; the Heroku `heroku-postbuild` is a no-op ("scheduler-only deploy: skipping web build") — the web app deploys via Vercel, Heroku only runs the scheduled ingest.

**Unit tests** run on Node's built-in test runner via tsx and live in both workspaces. The `scripts/` suite (`node --import tsx --test "**/*.test.ts"`) and the `web/` suite (`node --import tsx --test "lib/**/*.test.ts"`) are each wired up as the `test` script in their package.json. Run a single workspace with `pnpm --filter edgeboard-scripts test` / `pnpm --filter edgeboard-web test`, or both at once with `pnpm test` from the repo root (recursive). No jest/vitest. ## Architecture and data flow

The system is a **batch-compute-then-serve** design. The web app never computes metrics; it only reads pre-computed rows — with one deliberate exception (below): the Market Analytics page reads missing market metadata / price history live from Polymarket so a market a user opens is never blank.

Ingestion (`scripts/ingest.ts` `main()`):
1. `discoverTopWallets()` (`polymarket.ts`) seeds wallets from Polymarket's `/v1/leaderboard`, falling back to `/trades` if that fails.
2. **Candidate discovery** (`discoverCandidateAddresses`): queries 5 additional `/v1/leaderboard` permutations (ALL/PNL, 1m/VOL, 1m/PNL, 1w/VOL, 1w/PNL) plus the live `/trades` stream to find traders the main VOL-sorted discovery misses. New addresses are inserted into `candidate_wallets` with `ignoreDuplicates: true` (never overwrites existing status). `tracked` candidates are loaded and merged into the main wallet list so they compete for leaderboard slots every full run.
3. For each wallet (worker pool, `WALLET_CONCURRENCY` in flight): fetch `/activity` → `isSuspectedBot()`, plus `recentTradesFromActivity()` (feed) and `profileFillsFromActivity()` (last-N fills); fetch `/closed-positions` → `computeMetrics()` for each horizon in `CONFIG.HORIZONS` (30/90 days). Also derives `openPositionRecords()`, per-wallet closed-position basis records, and the distinct **outcome-token ids (`assets`)** the wallet held in-window (union of closed + current) — these seed the price-history cache. The max horizon also bounds how far back `getClosedPositions` paginates, so it drives ingest API cost. The web app's `HORIZONS` (`web/lib/types.ts`) matches: only 30 and 90 are exposed. (The 365-day horizon was removed end-to-end; the schema's `horizon_days IN (30, 90, 365)` CHECK constraints still permit 365 but nothing writes it.)
4. Upsert into `wallet_stats` and `equity_curve`; collect recent trades, profile fills, open positions, closed positions, and assets.
5. `rebuildLeaderboardCache()` re-derives `leaderboard_cache`: orders by `skill_score`, **excludes bot-suspected wallets**, keeps top `TOP_N`.
6. **Candidate batch scoring** (`scoreCandidateBatch`): selects up to `CANDIDATE_BATCH_PER_RUN` (500) unscored/stale `candidate` wallets and runs them through the same `processWallet` pipeline. Reads back their `wallet_stats` scores; wallets that reach `CANDIDATE_PROMOTION_THRESHOLD` (4.0 = `SCORE_FLOOR`) are promoted to `tracked`. Previously-scored candidates are skipped for `CANDIDATE_RESCORE_DAYS` (30) between passes so confirmed low-scorers don't consume the batch. **Tracked candidates whose main-pool scores drop below `CANDIDATE_RETIREMENT_THRESHOLD` (3.0) for 3 consecutive full runs are retired** and never scored again (`updateTrackedCandidateStatuses`).
7. **Board-scope the collected detail, then persist it.** Right after `rebuildLeaderboardCache` (step 5) — *before* the candidate batch (step 6) and the memory-heavy tail — every collected buffer (recent trades, profile fills, open/closed positions, plus `assetsByAddress`/`entryDatesByAddress`) is filtered down to the `getLeaderboardAddresses` set, **freeing the non-board majority early**. The pass accumulates detail for every *eligible* wallet (hundreds), but only the ~`TOP_N` leaderboard wallets are ever persisted or read back (the feed, positions, and Convergence read paths all filter on leaderboard membership), so the rest is dead weight. The board-only rows are then wipe-and-replaced per table (`recent_trades` / `wallet_trades` / `wallet_positions` / `wallet_closed_positions`). This keeps peak memory proportional to `TOP_N` rather than the full eligible set — the daily full ingest had been OOM-killed (R15/SIGKILL, ~1 GB) on the 512 MB dyno doing it the old way (see the dyno-memory note under Local dev & deployment gotchas). **Consequence:** a non-board but *eligible* wallet keeps its `wallet_stats` score but carries no position/fill detail, so a direct `/wallet/[address]` visit shows an empty positions list (nothing in the UI links to such wallets).
8. `cacheMarketPriceHistory()` — the **only step that hits the CLOB API**. For every outcome token a leaderboard wallet held, pull `/prices-history` and cache a daily series in `market_price_history` (newest day per asset tracked in `market_price_meta`). Append-only + immutable: a token gone stale (no new daily point for `PRICE_HISTORY_STALE_DAYS`) is treated as resolved and never re-fetched, so the heavy first run amortizes to ~zero; a per-run fetch cap (`PRICE_HISTORY_MAX_FETCHES_PER_RUN`) defers overflow to later runs; rows older than the max horizon are pruned. Feeds the wallet mark-to-market equity curve.
9. `ingestMarkets()` — one global Gamma `/events` pass, `mapEvent()` per event, keep top `MARKETS_TOP_N` by liquidity into `markets`. Global, independent of wallet processing.

**Candidate pipeline** (`scripts/candidateDiscovery.ts` + `scripts/polymarket.ts` + `supabase/migrations/016_candidate_wallets.sql`): the main leaderboard discovery is biased toward high-volume traders. The candidate pipeline samples 5 additional leaderboard views and the recent-trades stream to find traders with genuine edge who never appear in the volume-sorted top 5,000. Lifecycle: `candidate` (discovered, not yet scored) → `tracked` (score ≥ `CANDIDATE_PROMOTION_THRESHOLD` = 4.0) → `retired` (3 consecutive below-threshold runs while tracked). All pure decision functions live in `candidateDiscovery.ts` (tested in `candidateDiscovery.test.ts`); all I/O in `ingest.ts`. Constants in `config.ts` under `CANDIDATE_*`.

Partial CLI modes skip most of this: `--feed-only` re-pulls just `/activity` for current leaderboard wallets and refreshes the feed (no scoring, no closed-positions); `--markets-only` runs just step 9; `--rescore-top` (`rescoreTopWallets`) re-scores just the standings (below). All three skip the candidate pipeline entirely.

**Hourly leaderboard rescore** (`--rescore-top`): the full ingest is expensive (5k+ wallets, deep closed-position pagination, price history) and runs daily, so between full passes the leaderboard drifts as markets resolve. This mode closes the gap cheaply enough to run hourly. It selects the top `RESCORE_TOP_N` (200) wallets **per horizon** from the already-scored `wallet_stats` (ranked exactly as `rebuildLeaderboardCache` ranks: `skill_score` desc, `avg_edge_per_share` desc), **dedupes across horizons** (`dedupeRescoreAddresses` — a wallet on both boards is scored once), runs each through the same `processWallet` pipeline the full ingest uses (re-pulling `/activity` + `/closed-positions` + `/positions`, recomputing every horizon's metrics into `wallet_stats` + `equity_curve`), then calls `rebuildLeaderboardCache` so the refreshed scores re-rank the board. The selection window is wider than `TOP_N` (200 vs 100) so wallets at ranks 101–200 can break in if their score improved; the rebuild ranks across *all* `wallet_stats`, so a rescored wallet whose score dropped correctly falls below an untouched one. Scope is deliberately just the standings — the activity feed is owned by `--feed-only` and the position caches / price-history equity curve by the daily full ingest, so the `recentTrades`/positions `processWallet` returns are discarded (same as the candidate batch) and `processWallet` is called with `writeEquityCurve=false` so the sparse realized curve never overwrites a board wallet's daily mark-to-market `equity_curve` (which would sawtooth until the next full ingest). It reads `wallet_stats`, so it requires a prior full ingest to have populated it (empty → no-op). A few hundred wallets instead of thousands, so it finishes in minutes.

**Market Analytics page** (`web/app/market/[conditionId]/page.tsx`) is the per-market deep dive, reachable by clicking any market on the Markets/Convergence/Resolved surfaces. `getMarketAnalytics(conditionId)` (supabase.ts) assembles the `markets` snapshot, the daily YES price series (from `market_price_history` via the YES outcome token), the leaderboard `CrowdMarketDetail`, and the tracked fills joined with each wallet's identity; the page derives every chart/metric at read time via the pure `web/lib/marketAnalytics.ts` helpers (see test list above). Sections: an interactive hand-rolled SVG `PriceChart` (hover crosshair/tooltip + whale-trade overlay + regime-shift markers), `WhaleFeed`, `ConcentrationChart`, `PnlHistogram`, a 3-way smart-money lean (headcount/capital/skill), the reused `ConvergenceChart`, and `CrowdParticipants`. Both `meta` and `detail` are independently nullable so the page degrades gracefully. Markets are clickable because `mapEvent` stores the leading market's `condition_id` (and `yesTokenId`) into the `markets` table. The **price series** is read from `market_price_history` by `condition_id` first, falling back to the leaderboard-held YES outcome token (asset): `ingest:markets` (`cacheListedMarketPrices`) caches a daily YES series for every listed market's leading CLOB token keyed by condition_id, so the chart works for any Markets-page market — not just ones a wallet holds. That cache is incremental via `market_price_meta` (a token already fresh-through-today is skipped), so the hourly markets run is a near no-op after the first daily fill. A market with no usable conditionId still falls back to plain text + an external Polymarket link.

**Live-enrichment fallback** (`web/lib/polymarketLive.ts`): the batch caches only cover top-`MARKETS_TOP_N` listed markets (meta) and leaderboard-held outcome tokens (price), and `market_price_history` stores only one CLOSE per day. A market opened from Convergence/a wallet page that's in neither set would otherwise render blank, and no market has cached daily high/low. So `getMarketAnalytics`, alongside the DB reads, fetches canonical data straight from Polymarket server-side:
- **Meta** via Gamma `/markets?condition_ids=` when there's no `markets` row (`fetchLiveMarket`; retries with `&closed=true` because Gamma's default filter hides resolved markets).
- **Intraday price line** via CLOB `/prices-history` (`fetchLivePriceSeries`): the cache stores one CLOSE per day, but the chart wants every intraday move so whale fills line up with the line. Three fidelities are fetched in parallel — daily (`1440`, full life), hourly (`60`), minute (`1`) — and `mergeSeries` stitches them finest-first: each finer series owns its window (it only reaches back ~1000 points) and coarser series fill the gap before it begins. The YES token comes from the listed-cache asset / a held position / Gamma meta (a NO token is inverted, `1 − p`). The merged series supersedes the close-only cache for the chart and the convergence price overlay.

- **Multi-outcome candidate lines** (`fetchEventCandidates` + `parseEventCandidates`): for a grouped event (e.g. one team in "World Cup Winner" — detected by the market's `groupItemTitle`), the chart overlays the **top-3 favored candidates**. The tracked market is the primary line (`priceRows`); the other top candidates' series are returned as `extraLines` (with `primaryLabel` for the legend). Gated to skip plain Yes/No markets (no extra Gamma call).

These calls use Next's Data Cache (`revalidate` 600s) so repeats/concurrent renders share one fetch; the meta + price fetches run concurrently when the token is known up-front. No write-back (web holds only the anon key). The price chart (`PriceChart`) is a **line** chart on a time axis with whale fills overlaid at their **YES-equivalent** price (a NO fill at 47¢ is plotted at YES 53¢ via `WhaleTrade.yesPrice`) so buys/sells sit on the line instead of scattering above/below it; for grouped events it draws the top-3 candidate lines (colors from `PRICE_LINE_COLORS`). `buildPriceSeries` keeps the raw intraday points for the line but derives the day-over-day stats (24h drift, daily-swing volatility, regime shifts) from a daily collapse. Pure helpers (`mapLiveMarketRow`, `mergeSeries`, `buildPriceSeries`, `detectWhaleTrades`'s `yesPrice`, `marketResolution`) are unit-tested. Net effect: **every** market renders a full-resolution price line. Also, fill-only participants (a wallet seen only via the capped fill cache) are marked to the current YES price for value/P-L in `buildCrowdMarketDetail`, except sells-only wallets whose cost basis predates the fill window (P/L left blank rather than overstated). Resolved markets show a `marketResolution` banner (winning side + whether the skill-weighted smart money called it).

Web read path: `web/lib/supabase.ts` is the only DB access layer — `getLeaderboard`, `getWalletProfile`, `getRecentLeaderboardTrades`, `getMarkets`, `getCrowdedMarkets`/`getCrowdMarketDetail`, `getMarketAnalytics`, plus the server/browser/write client factories. Pages (`web/app/page.tsx`, `leaderboard/`, `markets/`, `market/[conditionId]/`, `wallet/[address]/`, `early-access/`) and API routes (`web/app/api/{leaderboard,markets,recent-trades,crowded-markets,waitlist,wallet/[address]}`) call it. **Convergence** is split: the **ranked list** (`getCrowdedMarkets`) is **precomputed** by the daily full ingest into `crowded_markets_cache` (migration `018`) and read back as a tiny `ORDER BY rank LIMIT n`, while the **per-market detail** (`getCrowdMarketDetail`) is still aggregated **at read time** from the leaderboard-scoped position caches via the pure lib `web/lib/marketCrowd.ts` (`wallet_positions` + `wallet_closed_positions` + `wallet_trades` + `market_price_history`, filtered by `condition_id` so it stays small). **This split was deliberate** — the old `getCrowdedMarkets` scanned the *entire* `wallet_positions` table (paged via `fetchAllPaged`) and aggregated in-process on the home page's SSR path under a 1.5s timeout, which spiked Supabase CPU/memory/IO and frequently timed out to an empty Convergence section. The ingest now runs the same `summarizeCrowdedMarkets()` once (ingest-side port in `scripts/marketCrowd.ts` + `cacheCrowdedMarkets()`); keep the two `summarizeCrowdedMarkets` copies in sync. `crowded_markets_cache` is empty until the next full ingest repopulates it (e.g. after a `TRUNCATE` — see the Supabase gotcha below). The detail page renders `ConvergenceChart` (a hand-rolled SVG position-flow chart, same style as `WalletTelemetry`'s dive profile) and `CrowdParticipants` (expandable per-wallet fill ledgers). Leaderboard reads come straight from `leaderboard_cache`; wallet profiles join `wallet_stats` + `equity_curve` + `leaderboard_cache` (rank badges) + the wallet-detail tables (`wallet_positions`, `wallet_trades`, `wallet_closed_positions`). The equity curve is served from the precomputed `equity_curve` table — `web/lib/equityCurve.ts` (`windowedCurve`) only re-windows those points at read time; the web app never reads `market_price_history` (that cache feeds the ingest-time mark-to-market only). The waitlist route uses the **anon write client** (RLS allows INSERT, not SELECT). UI lives in `web/components/` (e.g. `LeaderboardTable`, `MarketsTable`, `RecentTradesFeed`, `WalletDossier`, `WalletActivity`, `WaitlistForm`, `OceanScene`).

**Access gate** (removed): the pre-launch waitlist gate has been **removed for public launch** — all routes are open by default. (Historically, production bounced every route except `/early-access` and `/api/waitlist` to the waitlist unless the visitor held an `eb_access` cookie, unlocked via `/unlock?key=<SITE_ACCESS_KEY>`. That flow and the `SITE_ACCESS_KEY` env var are no longer wired up; re-add the bounce logic to `web/middleware.ts` if a closed beta is ever needed again.)

**Maintenance mode** (`web/middleware.ts` — the `MAINTENANCE_MODE` env var): there *is* a `web/middleware.ts` again, but its only job now is a site-wide maintenance gate. When `MAINTENANCE_MODE` is one of `on`/`1`/`true`/`yes` (case-insensitive, trimmed), the middleware rewrites **every page navigation** to the standalone `/maintenance` page and answers `503` with `Retry-After: 3600` (so uptime monitors and crawlers treat it as an intentional, temporary outage). The matcher excludes `_next/`, `/api/`, `/maintenance`, and the static icons — so **API routes keep serving** and only user-facing pages get swapped. Any other value (or unset/deleted) = site runs normally. **Toggling it (it's a Vercel env var, so a change needs a redeploy to take effect — same gotcha as the Supabase keys):**
  - **On:** Vercel → project → Settings → Environment Variables → set `MAINTENANCE_MODE=on` (Production scope) → **redeploy** (Deployments → newest → ⋯ → Redeploy).
  - **Off:** clear/delete `MAINTENANCE_MODE` (or set any non-enabled value) → **redeploy**.
  - It's all-or-nothing and immediate (whole site, every page); there's no per-route or scheduled variant. The maintenance screen itself is `web/app/maintenance/page.tsx`, a fixed full-viewport overlay styled by the `.wm-page` / `.wm-*` rules in `globals.css` (the wrapper is `.wm-page`, **not** `.wm` — a bare `.wm` collided with BrandMark's wordmark `<div class="wm">` and hijacked the topnav into a full-screen overlay that hid the nav; see the topnav-collision note under Local dev & deployment gotchas).

### Scoring lives in two files
- `scripts/config.ts` — the **single source of truth** for every tunable threshold (horizons, min trades/volume, skill-score knobs `EDGE_SHRINKAGE_K`/`EDGE_FOR_TEN`/`SCORE_FLOOR`/`SCORE_MAX`, eligibility gates, bot heuristics, API pagination/retry, the Gamma/CLOB hosts, `MARKETS_TOP_N`, and the price-history knobs `PRICE_HISTORY_FIDELITY_MIN`/`PRICE_HISTORY_STALE_DAYS`/`PRICE_HISTORY_MAX_FETCHES_PER_RUN`). Change tuning here, not inline.
- `scripts/metrics.ts` — `computeMetrics` (per-horizon realized PnL, % return, win rate, forecasting edge, daily equity curve) and `computeSkillScore` (the Bayesian-shrunk edge score: 0 for zero/negative edge, else `[SCORE_FLOOR, SCORE_MAX]`; `null` for ineligible wallets: too few trades, too little volume, sub-cent longshot, or one win dominating PnL).

Bot detection (`scripts/botDetection.ts`): `botSignal()` flags wallets on the first of four signals — trades/day (`MAX_TRADES_PER_DAY`), min-avg-trade-size (`MIN_AVG_TRADE_SIZE_USD`), simultaneous open markets (`MAX_SIMULTANEOUS_MARKETS`), or **fast-flipper** (completed round-trips dominated by sub-`FAST_FLIP_MAX_HOURS` holds — `FAST_FLIP_FRACTION` of at least `FAST_FLIP_MIN_ROUNDTRIPS`). The fast-flipper signal excludes non-copyable arb/hedge/scalp churn (e.g. BTC 15-min markets) that evades the rate/size/breadth checks — Skill Score measures *copyable* forecasting edge, so legitimate human scalpers are out of scope too. Holding time is derived from the `/activity` fills already pulled (no extra API), in the same chronological replay that powers the simultaneous-markets count. Tune from the per-signal breakdown log (`Bot breakdown: trade_rate=… dust_trades=… simultaneous_markets=… fast_flipper=…`).

## Critical conventions and gotchas

- **The Supabase `Database` type is hand-maintained in two copies; there is no codegen.** It appears inline in `scripts/ingest.ts` and again in `web/lib/types.ts`. Each copy is a **subset of the migrations** typing only the tables that workspace touches — `scripts` (writes) has `market_price_history`/`market_price_meta` and omits `waitlist`; `web` (reads + the waitlist insert) has `waitlist` and `market_price_history` (read by the Convergence detail's YES-price overlay) but omits `market_price_meta`. That divergence is expected. The risk is the *shared* tables silently going out of sync with a migration: for columns the code actually selects, `strict` + `noUncheckedIndexedAccess` make `pnpm typecheck` catch it; for newly-added columns nothing references yet, update the relevant copy (or both) by hand.
- **`scripts/` is ESM (`NodeNext`) and imports use `.js` extensions** (e.g. `import { CONFIG } from "./config.js"` resolves to `config.ts`). Keep the `.js` suffix on relative imports there or `tsx`/`tsc` will fail. `web/` uses Bundler resolution and the `@/*` path alias — do not mix the styles.
- **Two TypeScript configs with different rules.** Both enable `strict`, `noUncheckedIndexedAccess`, and `exactOptionalPropertyTypes`, so optional props and indexed access need care.
- **Env vars** (copy `.env.example` → `.env.local`; root `.env.example` covers scripts, `web/.env.example` covers the web app):
  - web (browser-safe): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
  - scripts (writes): also needs `SUPABASE_SERVICE_ROLE_KEY`; optional `POLYMARKET_API_BASE`. `ingest.ts` loads `../.env.local` then a local `.env.local`.
  - Keep the **service-role key out of the web app** — the read path uses the anon key only.
- Polymarket's API field names are inconsistent, so `polymarket.ts` maps responses defensively via `readString`/`readNumber` with fallback key lists. When the API shape shifts, extend those key arrays rather than assuming one field name.
- Addresses are normalized to lowercase everywhere (ingestion, API routes, lib). Preserve this when adding lookups.
- **Polymarket rate limits** ([docs](https://docs.polymarket.com/api-reference/rate-limits)). We hit three hosts, each its own Cloudflare bucket over sliding 10s windows (requests are queued, not hard-rejected): the **Data API** (`data-api.polymarket.com`), the **Gamma API** (`gamma-api.polymarket.com`, markets), and the **CLOB API** (`clob.polymarket.com`, price history). Per-endpoint limits for the endpoints we call:
  - Data API `/closed-positions`, `/positions` — **150 req / 10s** (the binding constraint)
  - Data API `/trades` — **200 req / 10s**
  - Data API `/activity`, `/value`, `/v1/leaderboard` — fall under the general Data API limit of **1,000 req / 10s**
  - CLOB `/prices-history` — falls under the CLOB **General** limit of **9,000 req / 10s** (far above the Data API caps)

  `polymarket.ts` runs **one serial rate gate per lane** (`throttle(lane)`), keyed by `CONFIG.REQUEST_INTERVAL_MS`: `restricted` (`/closed-positions`, `/positions`), `general` (the rest of the Data API plus Gamma `/events`), and `clob` (CLOB `/prices-history`). Separate gates let cheap calls run in parallel with the expensive closed-position pagination, and keep the CLOB price-history backfill off the Data API budget entirely. Intervals target a comfortable fraction of each cap: restricted 90ms (~111 req/10s, under 150), general 30ms (~333 req/10s, under the ≥200 budget), clob 10ms (~1,000 req/10s, ~11% of the 9,000 cap — paced more by Supabase upserts than the gate). When tuning an interval down, keep that lane under its cap — `restricted` must stay ≥67ms (150/10s) and `general` ≥50ms (200/10s for `/trades`). `fetchJson` also honors the `Retry-After` header on a throttled response before exponential backoff.

## Local dev & deployment gotchas

The kind of thing that doesn't show up in the code and only bites you in production. **The web app and the ingest pipeline deploy to two different places from the same `master` branch, and only one of them is automatic.**

- **Don't run `pnpm build` / `pnpm start` while `pnpm dev` is running.** They share the `web/.next` build dir; running a production build against a dir `next dev` is using corrupts it, and the symptom is an unstyled / broken `localhost`. Stop `pnpm dev` first, or if it already happened, delete `web/.next` and restart.
- **Global CSS class-name collisions are silent and bite on deploy (seen in prod).** `globals.css` is one flat global stylesheet (no CSS Modules), so a class name reused for two unrelated things has the later/more-specific rule bleed onto both. A maintenance-page wrapper named `.wm` collided with BrandMark's topnav wordmark `<div class="wm">`: the maintenance rule (`position: fixed; inset: 0; z-index: 100`) hijacked the small wordmark into a **full-screen overlay that covered the nav links** — the Leaderboard/Markets/Signals buttons went invisible and unclickable, leaving only a centered "WHALEWATCHER". It surfaced only when current `master` (which first shipped the maintenance feature) deployed to prod, so it looked like "the homepage UI changed and broke navigation." Fixed by renaming the wrapper to `.wm-page`. **Diagnose this class of bug in-browser, not by reading CSS:** if an element is in the DOM/a11y tree but not visible, check what's actually painted on top of it — `document.elementFromPoint(cx, cy)` at the hidden element's center returns the covering element's class. When adding a new component, prefer a scoped/prefixed class (e.g. `.wm-*`) over a bare generic one, and grep `globals.css` for the name first.
- **Web app → Vercel, auto-deploys from GitHub `master`.** Pushing `master` triggers the Production build (branch pushes are Previews); Vercel project Root Directory is `web/`. Env-var changes (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`) only take effect on a *new* build — redeploy after changing them. The service-role key is intentionally **not** on Vercel.
  - *Rollback gotcha:* a Vercel **Instant Rollback** pins the domain to one deployment and stops new pushes from auto-promoting — symptom is "domain serves the old build even after I pushed." Fix: Deployments → newest `master` deploy → ⋯ → **Promote to Production**.
  - *Statically-prerendered API route gotcha (seen in prod, ROOT CAUSE):* a **no-argument `GET` route handler that reads no request data is statically prerendered by Next.js 14 at build time** — Next runs the handler **once during `next build`**, bakes that one JSON snapshot into the deployment, and serves it unchanged until the next deploy. The handler **never re-runs**, so the data freezes at deploy time even though the `Cache-Control: s-maxage=…` header it sets *looks* like it should refresh (that header only controls the CDN; it can't un-freeze a build-time-baked body). This hit `/api/recent-trades` (the home-page "Acoustic Log" feed) and `/api/crowded-markets` (Convergence): the feed froze at the deploy and its newest trade aged indefinitely while the whole backend was healthy (DB newest trade minutes old, Heroku feed cron green every 10 min, `getRecentLeaderboardTrades()` returning fresh data in ~700ms against the anon key locally). **Why a redeploy "fixed" it only temporarily:** redeploying rebuilds the snapshot fresh, then it re-freezes immediately — the freeze age always equals the time since the last deploy. **Tells:** (1) user-visible symptom is a stale "Nh ago" on the feed — that figure is `elapsedFrom(latestTradedAt)`, the age of the **newest baked-in trade**, which ages in real time, *not* a refresh clock; (2) `curl -sD - https://www.getwhalewatcher.me/api/recent-trades -o /dev/null` shows `Age` ≈ time-since-deploy with a persistent `X-Vercel-Cache: HIT` that only climbs; (3) `pnpm build` lists the route with `○ (Static)` instead of `ƒ (Dynamic)`. Distinguishes it from an Instant Rollback: the **home page** (ISR `revalidate=600`) keeps refreshing normally — only the no-arg routes freeze. **Why only these two routes:** the other data routes (`leaderboard`, `markets`, `wallet/[address]`, `decision-engine`) read `request.url`/`searchParams` or a dynamic `[param]`, which forces dynamic rendering, so they stayed live by accident. **Fix (permanent):** add `export const dynamic = "force-dynamic";` to the route so Next renders it on demand; the existing `s-maxage` `Cache-Control` header still makes the Vercel edge cache the response and hit the origin/Supabase only ~once per window, so this does **not** re-introduce per-request DB load (the egress rule's concern is per-request *uncached* scans — these stay CDN-cached). Confirm with `pnpm build` showing the route flip to `ƒ`. A redeploy/cache purge is only a stopgap; the `force-dynamic` export is the actual fix.
- **Ingest pipeline (`scripts/`) → Heroku app `edgeboard-ingest`, and it has NO auto-deploy.** It runs whatever slug was last `git push heroku master`'d, so pushing to GitHub master does **not** update it. **After any change under `scripts/`, run `git push heroku master` from the repo root** or the scheduled jobs keep running stale code. (This already caused a real bug: a markets fix was live on the site via Vercel but unpushed to Heroku for 13 commits, so the scheduled `ingest:markets` job kept overwriting the table with the old logic.) Check the deployed commit with `git fetch heroku && git rev-parse --short heroku/master`; env via `heroku config -a edgeboard-ingest`.
- **How the scheduled jobs actually fire (two mechanisms, not one).** The frequent partial refreshes do **not** run on Heroku Scheduler — they run through an always-on **webhook server** (`scripts/server.ts`, the Heroku `web` dyno, `pnpm webhook`) that an external **cron-job.org** account POSTs to on a schedule. The dyno stays awake because cron-job.org pings it every minute. Each route spawns the matching partial ingest and is single-flight (a 2nd ping while one runs gets `409 Already running`):
  - `POST /refresh/feed` → `pnpm ingest:feed` (~10 min cadence)
  - `POST /refresh/markets` → `pnpm ingest:markets` (~hourly)
  - `POST /refresh/rescore` → `pnpm ingest:rescore` (hourly — re-scores the top 200 wallets/horizon and rebuilds the leaderboard)

  All requests need `Authorization: Bearer $CRON_SECRET` (set via `heroku config:set CRON_SECRET=… -a edgeboard-ingest`); wrong/missing → `401`, unknown path → `404`, accepted → `202`. App URL: `https://edgeboard-ingest-ac4c7fff0498.herokuapp.com`. **This webhook pattern (vs. a Heroku Scheduler one-off dyno) is deliberate: hourly/10-min jobs would burn dyno hours as one-off dynos, so they reuse the already-running web dyno.** Only the **daily full `pnpm ingest`** runs as a Heroku Scheduler one-off dyno. **To change the cadence of feed/markets/rescore, edit the job in the cron-job.org account (not Heroku Scheduler); to add a new partial job, add a `/refresh/<mode>` route to `scripts/server.ts` + a cron-job.org job that POSTs to it.**

- **The full `pnpm ingest` is cadence-gated by `FULL_INGEST_EVERY_HOURS`.** `main()` no-ops (`Skipping full ingest: UTC hour N is not a multiple of M`) unless the current UTC hour is a multiple of that env var (Heroku config var = `4`, i.e. 00/04/08/12/16/20 UTC) — because Heroku Scheduler can't express "every N hours", so the daily job is scheduled hourly and self-skips. Unset/`0` disables the gate. **To force a full ingest right now regardless of the hour**, run it as a one-off with the gate off: `heroku run:detached "FULL_INGEST_EVERY_HOURS=0 pnpm ingest" -a edgeboard-ingest` (the inline override doesn't touch the app's config var). The partial modes (`--feed-only` etc.) are not gated.

- **The daily full ingest runs on a 512 MB dyno and is memory-bound.** Heroku **Eco and Basic dynos are both 512 MB** (Basic does *not* add memory — only leaving for the Standard tier does: Standard-2X = 1 GB). The full ingest processes ~5k wallets, so it's the one job that flirts with the ceiling. Heroku signals **R14** (memory quota exceeded) above 512 MB — this only *throttles/swaps*, the process survives — and **R15** (vastly exceeded, ~2×/~1 GB) which **`SIGKILL`s it (exit 137)**. So the budget to respect is the R15 line, not R14. Two things keep it under: the **board-scoping in ingestion step 7** (peak ∝ `TOP_N`, not the full eligible set) and the write-once buffer frees (`collected*.length = 0`) before the tail. This has bitten twice — an OOM kill mid-tail, and a `HeadersOverflowError` from an under-chunked `.in()` (see the `.in()` chunking rule in the Supabase design-rules section below). When adding to the tail, prefer streaming/paged reads over loading a whole table into memory.

## Supabase load & the "overloaded DB" recovery playbook

The Supabase instance is on a **small free tier** with two distinct, easy-to-blow limits: a **compute ceiling** (it has hit 100% CPU / high memory / high disk-IO under sustained write churn and per-request full-table scans) and a **5 GB / month egress budget** (total bytes the project serves *out* — read responses to the web app; overage → the project gets restricted). Both are driven by the same anti-pattern — **reading more rows, more often, than a request needs** — so the design rules below guard against both. Root causes seen in production, their fixes, and how to dig out when the DB is wedged:

- **Per-request full-table scans (fixed).** The old `getCrowdedMarkets` scanned all of `wallet_positions` on every home-page render. Now precomputed into `crowded_markets_cache` by the ingest (see the Convergence note above). Any *new* read path that scans a whole table per request — or a page that drops ISR for `force-dynamic` — will re-introduce this; precompute into a cache table instead.
- **Egress blowout from over-fetching read paths (fixed).** The project exceeded the 5 GB/month egress budget (6.85 GB). Cause: `getRecentLeaderboardTrades` (the home-page feed) downloaded the *entire* position cache — `wallet_positions` + `wallet_closed_positions` + `wallet_trades` for every leaderboard wallet, thousands of rows — just to derive cost-basis for ≤200 displayed trades, and clients poll `/api/recent-trades` every 60s while the edge cache held only 60s, so that scan re-ran ~once/minute all day. Two-part fix: (1) **lengthen cache windows to match data cadence** — `/api/recent-trades` `s-maxage` 60→600 (feed only changes on the ~10-min cron), `/api/markets` 60→300, home-page `revalidate` 300→600 (commit `c0fb06c`); (2) **scope the read to what's shown** — the basis lookups now filter to the feed's `condition_id`s (the maps are only read at keys present in the feed), chunked 60 ids/request to stay under PostgREST's ~22 KB URL limit (commit `f5747de`). Still-secondary scanners if more reduction is needed: `/api/wallet/[address]` and `/api/decision-engine`.
- **Job churn / misconfiguration (the real incident).** The cron-job.org **feed** job had been set to **every 1 minute** (not the intended ~10), *and* a duplicate `ingest:feed` job existed in **Heroku Scheduler** — so two sources spawned overlapping feed runs that crash-looped (`upstream request timeout` against the maxed DB) and pinned the instance. **Keep feed at ≥10 min cadence, from exactly one source (cron-job.org), and never duplicate a partial job in Heroku Scheduler.** The wipe-and-replace tables (`recent_trades` + `wallet_trades` are the highest-churn, rewritten every feed run) generate dead-tuple bloat in proportion to job frequency.
- **Reclaiming disk bloat.** `VACUUM FULL` **cannot run through the Supabase SQL editor** — it rewrites the whole table and exceeds the editor's HTTP gateway timeout (and an editor timeout does *not* stop the VACUUM; Postgres keeps running it, holding an `ACCESS EXCLUSIVE` lock). For the wipe-and-replace **cache** tables, `TRUNCATE` instead — instant, and the next ingest refills them. `supabase/maintenance/reclaim_bloat.sql` lists the churned tables. **Do NOT truncate `market_price_history` / `market_price_meta`** (append-only + immutable; truncating forces an expensive full CLOB re-fetch), **`wallets`**, or **`candidate_wallets`** (accumulated lifecycle state). After a `TRUNCATE`, run a full ingest to refill (and to repopulate `crowded_markets_cache`).
- **When the DB is wedged** (even a trivial query in the SQL editor returns `Connection terminated due to connection timeout`): that's lock/connection-pool exhaustion, not a slow query — usually an orphaned `VACUUM FULL` still executing server-side plus zombie connections from crash-looping jobs. Recovery, in order: (1) stop the writers — `heroku ps:scale web=0 -a edgeboard-ingest` (halts the webhook-driven partials; the website on Vercel is unaffected) and **pause the Heroku Scheduler jobs** in its dashboard; confirm nothing is running with `heroku ps -a edgeboard-ingest`; (2) **restart the Supabase project** (Dashboard → Settings → General → Restart) to force-clear stuck queries and free the connection pool; (3) run any pending migration + `TRUNCATE` promptly while the DB is quiet; (4) force a full ingest to refill (command above); (5) re-scale `heroku ps:scale web=1` and re-enable the (single, ≥10-min) Scheduler/cron jobs once healthy.

### Design rules for any new read path or feature (keep Supabase within its limits)

Because the tier is small on **both** compute and egress, treat the database as a scarce resource on every new feature. Before adding a query, page, or API route, work through these:

1. **Never scan a whole table per request.** Always constrain reads with `.eq()` / `.in()` on an indexed column scoped to what the request actually renders (a wallet, a market, the leaderboard set) — not "all rows, then filter in JS." If a feature *needs* a board-wide aggregate (e.g. Convergence, resolved-markets), **precompute it into a cache table during ingest** (the `crowded_markets_cache` pattern) and have the web read the small result — the web app never computes metrics (see Architecture).
2. **Select only the columns you use.** No `select("*")` on wide/high-row tables; list the exact columns (every extra column is egress on every row of every request).
3. **Fetch only the rows the response shows.** When you need related rows (cost-basis, handles, ranks), derive the key set from the primary result and `.in(...)` on *those* keys — don't pull a wallet's entire history to use 3 rows of it. Chunk large `.in()` lists **by value length** to stay under PostgREST's ~16 KB request-URL limit — overflow throws a `HeadersOverflowError` (`UND_ERR_HEADERS_OVERFLOW`) that aborts the run, not a graceful error. The ingest sizes its chunks per id type: `LEADERBOARD_FILTER_CHUNK` (200) for 42-char wallet addresses, `ASSET_FILTER_CHUNK` (100) for ~77-char CLOB token ids (200 of those serialized to a 16 KB URL and crashed `loadPricesForAssets`).
4. **Cache at a window that matches how often the data actually changes.** The data only refreshes on the ingest cadence (feed ~10 min, markets/rescore ~hourly, full ingest daily), so set API `Cache-Control: s-maxage` and page `export const revalidate` to that cadence — a 60s cache on data that changes every 10 min just re-reads the same bytes 10× for nothing. **Never use `force-dynamic` / `no-store` on a Supabase-backed page** unless it's truly per-user and uncacheable.
5. **Mind client polling × cache window.** Components poll their `/api/*` route every 60s (`POLL_INTERVAL_MS`); the edge cache collapses concurrent pollers into one origin read per `s-maxage` window, so the *cache window*, not the poll interval, sets DB load. A heavy uncached endpoint behind a 60s poll is a full scan every minute, all day.
6. **Writes: prefer upsert/wipe-and-replace on cache tables over high-frequency churn.** Every rewritten row is dead-tuple bloat proportional to job frequency (`recent_trades`/`wallet_trades` are the worst); keep the partial-refresh cadence at the documented intervals.

When in doubt, ask: *"Does this read scale with rows-shown, or with table-size? And how often does it really need to re-run?"* If the answer is "table-size" or "every request," redesign it (scope it, or precompute a cache table) before shipping.
