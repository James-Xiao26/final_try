# CLAUDE.md

Guidance for Claude Code in this repo. These instructions OVERRIDE default behavior.

## What this is

EdgeBoard (deployed as **WhaleWatcher**, getwhalewatcher.me) ranks Polymarket traders by a 0–10 "Skill Score" = purely statistical forecasting edge (how reliably a trader's entry prices beat the market's eventual resolution, Bayesian-shrunk for sample size), not raw PnL. Surfaces: leaderboard, **Markets** page, a home-page **Trending** panel (leaderboard-driven "smart money" signal vs. live price), **recent-trades feed** with a **Convergence** ("crowded markets") sub-section + per-market detail, and per-wallet **detail** (open/closed positions with P/L, a copy-trade equity curve).

pnpm monorepo, two workspaces:
- `scripts/` (`edgeboard-scripts`) — TS ingestion pipeline run via `tsx`. Pulls Polymarket public APIs (Data + Gamma + CLOB), computes metrics, writes Supabase.
- `web/` (`edgeboard-web`) — Next.js 14 App Router frontend. Reads pre-computed Supabase rows, **never computes metrics**. Read-only against Polymarket except the Market Analytics live-enrichment fallback (`web/lib/polymarketLive.ts`).
- `supabase/migrations/` — Postgres schema (25 migrations).

## Architecture and data flow

**Batch-compute-then-serve.** The web app never computes metrics; it reads pre-computed rows — except Market Analytics reads missing market metadata/price history live so an opened market is never blank.

### Ingestion (`scripts/ingest.ts` `main()`)
1. `discoverTopWallets()` — seed from `/v1/leaderboard`, fall back to `/trades`.
2. **Candidate discovery** (`discoverCandidateAddresses`) — query 5 more `/v1/leaderboard` permutations (ALL/PNL, 1m/VOL, 1m/PNL, 1w/VOL, 1w/PNL) + `/trades` to find traders the VOL-sorted main discovery misses. New addresses inserted into `candidate_wallets` with `ignoreDuplicates`. `tracked` candidates merge into the main list to compete for slots each full run.
3. **Tiered recheck cooldown filter** (`scripts/walletRecheck.ts` `shouldSkipWallet`) — before the worker pool starts, the discovered + tracked-candidate set is bulk-checked against each wallet's last-known state (`wallets.is_bot_suspected`/`updated_at`/`earliest_trade_at`, `wallet_stats.skill_score`/`ineligible_reason`/`computed_at`) and filtered down to only the wallets worth re-fetching. See "Tiered wallet recheck cooldown" below.
4. Per wallet (worker pool, `WALLET_CONCURRENCY`): fetch `/activity` → `isSuspectedBot()`, `detectArbitrageConditions()`, `recentTradesFromActivity()`, `profileFillsFromActivity()`; fetch `/closed-positions` → filter out arb-flagged conditionIds (`excludeArbitrage`) → `computeMetrics()` per horizon in `CONFIG.HORIZONS` (30/90). Derives `openPositionRecords()`, closed-position basis records, and the distinct outcome-token ids (`assets`) held in-window (seeds price-history cache). Max horizon bounds `getClosedPositions` pagination, so it drives ingest API cost. Web `HORIZONS` (`web/lib/types.ts`) matches (30/90 only). (365 removed end-to-end; schema CHECK still permits it but nothing writes it.)
5. Upsert `wallet_stats` (+ `ineligible_reason`, `wallets.earliest_trade_at`) + `equity_curve`; collect trades/fills/positions/assets.
6. `rebuildLeaderboardCache()` — re-derive `leaderboard_cache`: order by `skill_score`, **exclude bot-suspected**, keep top `TOP_N`.
7. **Candidate batch scoring** (`scoreCandidateBatch`) — select up to `CANDIDATE_BATCH_PER_RUN` (500) unscored/stale `candidate` wallets through `processWallet`. **Candidate load paged with `.range()` in 1000-row chunks** (PostgREST hard-caps a response at 1000 rows regardless of `.limit()`). Wallets reaching `CANDIDATE_PROMOTION_THRESHOLD` (4.0 = `SCORE_FLOOR`) → `tracked`. Previously-scored skipped for `CANDIDATE_RESCORE_DAYS` (30). Tracked wallets below `CANDIDATE_RETIREMENT_THRESHOLD` (3.0) for 3 consecutive full runs → `retired`.
8. **Board-scope collected detail, then persist.** Right after step 6 — before step 7 and the memory-heavy tail — every buffer (trades, fills, positions, `assetsByAddress`) is filtered to the `getLeaderboardAddresses` set, freeing the non-board majority early. Only ~`TOP_N` wallets are persisted/read back. Board-only rows then wipe-and-replaced per table (`recent_trades`/`wallet_trades`/`wallet_positions`/`wallet_closed_positions`). Keeps peak memory ∝ `TOP_N` (the old way OOM-killed the 512 MB dyno, R15/SIGKILL ~1 GB). **Consequence:** a non-board but eligible wallet keeps its `wallet_stats` score but carries no detail, so a direct `/wallet/[address]` visit shows empty positions (nothing links to such wallets).
9. `cacheMarketPriceHistory()` — **the only step hitting CLOB.** For every outcome token a leaderboard wallet held, pull `/prices-history` → daily series in `market_price_history` (newest day per asset in `market_price_meta`). Append-only + immutable: a token stale for `PRICE_HISTORY_STALE_DAYS` is treated as resolved and never re-fetched; per-run cap `PRICE_HISTORY_MAX_FETCHES_PER_RUN`; rows older than max horizon pruned. Feeds web price charts (Convergence YES overlay + Market Analytics) — **not** the equity curve.
10. `ingestMarkets()` — one global Gamma `/events` pass, `mapEventCandidates()` per event (every candidate market in the event, not just the leading one — a grouped event like an election gets one row per candidate, each with its own `condition_id`/liquidity/volume, so a non-leading candidate can still surface on Markets/Trending once it has real activity; zero-liquidity-and-zero-volume placeholder candidates are pruned, then kept candidates are capped to `MARKETS_MAX_CANDIDATES_PER_EVENT` (8) by liquidity **per event** so one large election/tournament can't crowd out unrelated events), pool across all events, keep top `MARKETS_TOP_N` by liquidity into `markets`. `mapEvent()` still exists standalone (single-leading-candidate shape) and backs `getMarketAnalytics`'s event lookup. `id = conditionId ?? eventId` — full delete+insert every run, so no cross-run id-stability requirement. Global, independent of wallets.

### Candidate pipeline
`scripts/candidateDiscovery.ts` + `polymarket.ts` + migration 016. Main discovery is volume-biased; this samples 5 more leaderboard views + the recent-trades stream to find edge that never appears in the top 5,000 by volume. Lifecycle: `candidate` → `tracked` (≥4.0) → `retired` (3 consecutive below-3.0 while tracked). All pure decision functions in `candidateDiscovery.ts`; all I/O in `ingest.ts`. Constants under `CANDIDATE_*` in `config.ts`. **Known gap (not yet fixed):** a wallet is only registered into `candidate_wallets` (and so only gets a *permanent* recheck guarantee once `tracked`) if it was found via the candidate-specific sources — a wallet that earns a real score purely by staying in the daily top-5,000-by-volume main discovery has no such backstop. If it later drops out of that list, nothing rediscovers it and its score goes stale. Measured live (2026-07-02): 590 of 1,408 currently-eligible wallets have no `candidate_wallets` row at all; only 4 were actually stale (untouched >1 week), so current impact is small, but it grows over time. Fix (not implemented): register every currently-eligible main-discovery wallet into `candidate_wallets` too, even when it wasn't independently found by the extra candidate sources.

### Tiered wallet recheck cooldown
`scripts/walletRecheck.ts` (`shouldSkipWallet`) + migration 027. The main ~5k-wallet discovery loop re-fetched `/activity` + `/closed-positions` + `/positions` for every discovered wallet on *every* full run, with no memory of last run's outcome — most of that is wasted, since bot status and thin-volume ineligibility are largely persistent week to week, and the bottleneck is the throttled restricted API lane (`/closed-positions`/`/positions`, ~111 req/10s), not compute. Before the worker pool starts, `main()` bulk-loads each discovered/tracked wallet's last-known state and skips re-fetching it if it's still within its cooldown — **tiered by *why* it was flagged**, since each reason resolves on a different timescale (`CONFIG.WALLET_RECHECK`):
- **Bot-suspected** (`wallets.is_bot_suspected` + `updated_at`) — `BOT_DAYS` (45), the longest: an automated strategy rarely stops.
- **Insufficient trades/volume** (`wallet_stats.ineligible_reason` = `insufficient_trades`/`insufficient_volume`) — `THIN_SAMPLE_DAYS` (7), the shortest: a genuinely active trader can cross the gate within days.
- **Longshot entry** (`ineligible_reason` = `longshot_entry`) — `LONGSHOT_DAYS` (21), a structural trading-style flag, medium.
- **Too new** (`ineligible_reason` = `too_new`, the age gate) — not a fixed window at all; computed exactly from `wallets.earliest_trade_at + MIN_ACCOUNT_AGE_DAYS`, since it resolves on a known calendar date.

A wallet with a non-null score on *any* horizon is **never** skipped, regardless of tier — only confirmed bot/ineligible wallets are eligible for skip. `ineligible_reason` is computed by `ineligibilityReason()` (`scripts/metrics.ts`), a sibling to `computeSkillScore` (not folded in, so `computeSkillScore`'s exact-constant-asserted tests didn't need touching) — same 3-gate logic (min trades/volume/avg-entry-price), returned as a reason code instead of a bare null; the age-gate override (`processWallet`, `ingest.ts`) sets it to `too_new` directly since that signal comes from `/activity`, which `computeMetrics` never sees. **Two-run bootstrap:** `ineligible_reason`/`earliest_trade_at` are new, empty columns — the first full run after this shipped couldn't skip on those tiers yet (every previously-null-score wallet had to be reprocessed once just to populate the reason), but the bot tier could skip immediately since `is_bot_suspected`/`updated_at` are old columns with real history. Measured live: discovered set dropped from ~5,416 to 686 wallets needing actual reprocessing once fully warmed up (bot=3440, thin=901, longshot=67, too_new=322 skipped) — roughly an 8x cut in restricted-lane work for the main loop specifically (markets/price-history/candidate-scoring overhead is unaffected). Scope: main loop only — the candidate pipeline keeps its own flat `CANDIDATE_RESCORE_DAYS` cooldown, untouched.

### Partial CLI modes
- `--feed-only` — re-pull `/activity` + `/positions` for leaderboard wallets; refresh feed **and** `wallet_positions` (no scoring/closed-positions), so Current Positions stays as fresh as Trade History.
- `--markets-only` — just step 10.
- `--rescore-top` (`rescoreTopWallets`) — re-score just the standings (below).
- `--candidates-only` — **only** step 7, nothing else. Manual one-off to drain a large unscored backlog, paired with a high override: `CANDIDATE_BATCH_PER_RUN=15000 pnpm ingest --candidates-only` (on Heroku wrap in `heroku run:detached "…" -a edgeboard-ingest`). Safe to re-run; already-scored stay skipped for `CANDIDATE_RESCORE_DAYS`.

The first three skip the candidate pipeline entirely.

### Hourly leaderboard rescore (`--rescore-top`)
Full ingest is expensive (daily); between passes the board drifts as markets resolve. This closes the gap cheaply (hourly). Selects top `RESCORE_TOP_N` (200) wallets **per horizon** from `wallet_stats` (ranked as `rebuildLeaderboardCache`: `skill_score` desc, `avg_edge_per_share` desc), **dedupes across horizons** (`dedupeRescoreAddresses`), runs each through `processWallet` (re-pull `/activity` + `/closed-positions` + `/positions`, recompute every horizon into `wallet_stats` + `equity_curve`), then `rebuildLeaderboardCache`. Window wider than `TOP_N` (200 vs 100) so ranks 101–200 can break in. Scope = standings **plus** `wallet_positions` (scoped-replaced for the rescored set from the `/positions` already pulled). Feed owns the activity feed; daily full owns closed-positions + copy-trade `equity_curve`, so rescore discards those `processWallet` returns and calls it with `writeEquityCurve=false`. Reads `wallet_stats`, so needs a prior full ingest (empty → no-op).

### Market Analytics page (`web/app/market/[conditionId]/page.tsx`)
Per-market deep dive, reachable from Markets/Convergence/Resolved surfaces. `getMarketAnalytics(conditionId)` (supabase.ts) assembles the `markets` snapshot, the daily YES price series, the leaderboard `CrowdMarketDetail`, and tracked fills joined with wallet identity. Page derives charts/metrics at read time via pure `web/lib/marketAnalytics.ts`. Sections: SVG `PriceChart` (crosshair/tooltip + whale overlay + regime-shift markers), `WhaleFeed`, `ConcentrationChart`, `PnlHistogram`, 3-way smart-money lean, `ConvergenceChart`, `CrowdParticipants`. `meta` and `detail` independently nullable → graceful degrade. Markets are clickable because `mapEvent` stores the leading market's `condition_id` + `yesTokenId`. Price series read from `market_price_history` by `condition_id` first, falling back to the leaderboard-held YES token; `ingest:markets` (`cacheListedMarketPrices`) caches a daily YES series for every listed market keyed by condition_id (incremental via `market_price_meta`, near no-op after first fill). A market with no usable conditionId falls back to text + an external Polymarket link.

### Live-enrichment fallback (`web/lib/polymarketLive.ts`)
Batch caches only cover top-`MARKETS_TOP_N` markets (meta) + leaderboard-held tokens (price), one CLOSE/day. So `getMarketAnalytics` also fetches canonical data server-side:
- **Meta** via Gamma `/markets?condition_ids=` when no `markets` row (`fetchLiveMarket`; retries with `&closed=true` since Gamma hides resolved by default).
- **Intraday line** via CLOB `/prices-history` (`fetchLivePriceSeries`): three fidelities in parallel — daily (`1440`, full life), hourly (`60`), minute (`1`) — `mergeSeries` stitches finest-first (each finer series owns its window ~1000 points, coarser fills the gap before it begins). YES token from listed-cache asset / held position / Gamma meta (NO inverted, `1 − p`). Merged series supersedes the close-only cache for the chart + convergence overlay.
- **Multi-outcome candidate lines** (`fetchEventCandidates` + `parseEventCandidates`): for a grouped event (detected by `groupItemTitle`), overlay top-3 favored candidates. Tracked market = primary line (`priceRows`); others returned as `extraLines`. Gated to skip plain Yes/No markets.

These use Next Data Cache (`revalidate` 600s); no write-back (web holds only anon key). `PriceChart` is a **line** chart on a time axis with whale fills overlaid at their **YES-equivalent** price (a NO fill at 47¢ plots at YES 53¢ via `WhaleTrade.yesPrice`); grouped events draw top-3 candidate lines. `buildPriceSeries` keeps raw intraday points for the line but derives day-over-day stats from a daily collapse. Fill-only participants are marked to current YES price for value/P-L, except sells-only wallets whose cost basis predates the fill window (P/L blank, not overstated). Resolved markets show a `marketResolution` banner.

### Web read path
`web/lib/supabase.ts` is the only DB access layer — `getLeaderboard`, `getWalletProfile`, `getRecentLeaderboardTrades`, `getMarkets`, `getCrowdedMarkets`, `getMarketAnalytics`, + server/write client factories. Pages and `web/app/api/*` routes call it.

**Convergence is split:** the **ranked list** (`getCrowdedMarkets`) is **precomputed** by the daily full ingest into `crowded_markets_cache` (018) and read as a tiny `ORDER BY rank LIMIT n`; the **per-market detail** is aggregated **at read time** inside `getMarketAnalytics` (`buildCrowdMarketDetail`) from leaderboard-scoped caches via `web/lib/marketCrowd.ts` (filtered by `condition_id` so it stays small). **The split is deliberate** — the old `getCrowdedMarkets` scanned the *entire* `wallet_positions` table per home-page render under a 1.5s SSR timeout and frequently timed out to empty. Ingest now runs the same `summarizeCrowdedMarkets()` once (port in `scripts/marketCrowd.ts` + `cacheCrowdedMarkets()`); **keep the two copies in sync.** It ranks only markets with ≥1 *current* holder (`openCount > 0`) so a settled market can't sit atop Convergence forever. Cache rebuilt only by full ingest; empty until the next full pass (e.g. after a TRUNCATE).

**Leaderboard** reads straight from `leaderboard_cache`, with the per-wallet **specialty chip** + **leaderboard chips** on the same `wallets` join that supplies handles (`getLeaderboard` selects `handle, specialty, leaderboard_chips` in one scoped `.in()`). **Leaderboard chips** mark which Polymarket leaderboards a wallet ranks on with its rank: the full ingest's `scanChipBoards` (`polymarket.ts`) scans PnL + Volume boards (all-time/monthly/weekly — `CONFIG.CHIP_BOARDS`) to `PNL_BOARD_CHIP_TOP_N` (env-overridable, 1000); `cacheLeaderboardChips` stamps `wallets.leaderboard_chips` as `"code:rank"` (e.g. `"pnl-all:3"`); web `parseChip` renders them (PnL green/blue, Volume amber). **Full-ingest-only** — refreshes ~daily, null until first full ingest after 024/025.

**Wallet profiles** join `wallet_stats` + `equity_curve` + `leaderboard_cache` (rank badges) + detail tables. **Trade history** (`web/lib/walletTrades.ts`): `groupWalletTrades` collapses the last ~`PROFILE_TRADES_LIMIT` (200) fills into per-position groups; `applyClosedBasis` merges the closed-positions cache (backfills avg entry/bought-shares, attaches realized P/L + %, **and appends synthetic rows for closed positions with no fill group** — a single-market scalper can saturate the 200-fill window). `getWalletProfile` falls back to a live read (`fetchLiveWalletDetail`) when *either* positions or trades cache is empty (filling just the empty side; also filters `redeemable` resolved-but-unredeemed positions).

**Equity curve** = copy-trade sim (`scripts/equityCurve.ts` `simulateCopyCurve`, computed at full-ingest time into `equity_curve` by `writeDailyEquityCurves`): per horizon window, *"start $100, stake 1% of running balance to copy every trade — whole shares, $100 resets per window — what's my balance?"* Closed trades step the balance on close date (ride to final resolution $1/$0, or fall back to the trader's realized result when outcome unknown); open positions add one **today mark-to-market** at `curPrice`. Stored `cumulative_pnl` is a dollar **balance** starting at $100, not a delta. `web/lib/equityCurve.ts` (`windowedCurve`) re-windows at read time; `WalletTelemetry` renders **% return vs the $100 stake** on a y-axis fitted to data (no forced zero; breakeven line only when in range). Web reads `market_price_history` only for the Convergence YES overlay + Market Analytics — **not** the equity curve.

**Two equity-curve data quirks** (both fixed; don't reintroduce): (1) **future-dated points** — Polymarket sometimes reports a sold position's `closeTime` as the market's *future* end date, so `buildDailyCurve` could plot past today and `windowedCurve` (which uses the last point as the right edge) made it "today". Guarded twice: `buildDailyCurve` clamps a future close into today; `windowedCurve` drops future-dated points. (2) **unbounded-compounding overflow** — 1% stakes compounded on sub-penny longshots can blow $100 past $1T, overflowing `NUMERIC(14,2)` and crashing ingest; `simulateCopyCurve` clamps every point to `MAX_BALANCE` (1e11), floor 0. (Old mark-to-market curve + its plumbing is gone; upgrade path for steep longshot curves is a log-scale y-axis.)

**Trending** (`getTrendingMarkets`, home page, `TrendingPanel.tsx`): a leaderboard-driven "what's actionable right now" panel, distinct from Convergence's plain crowd-size ranking. Read-time aggregation scoped to a small known set of `condition_id`s (same exception `getMarketAnalytics` relies on, fanned out to `limit` markets), backed by one board-scoped `wallet_positions` read. `web/lib/trendingMarkets.ts` (pure): a market **qualifies** only with `TRENDING_MIN_PARTICIPANTS` (5) distinct wallets each holding a non-dust (`TRENDING_DUST_FLOOR_USD`, $10) position; qualifying markets are **scored** by three additive terms — resolving soon, still near what smart money's track record implies, and (sports/esports categories only) starting soon — and truncated to `limit`. The card's "Smart Money %" is `smartMoneyImpliedPrice`: a skill-weighted (`skill · √cost`, dampens a big bet from a mediocre trader without ignoring conviction) mean YES-equivalent entry price (NO entries inverted, `1 − avgPrice`) across the qualifying wallets — directly comparable to the market's live price. **Card price-scale gotcha (fixed, don't reintroduce):** `market.currentPrice` shows whichever side is currently *leading* (Yes or No), but `smartMoneyPct` is always YES-equivalent — comparing them raw is wrong for a No-leading plain-binary market. `TrendingPanel.tsx`'s `yesEquivalentLivePrice()` normalizes the live price to the same YES scale before the two are shown together. Validated offline by `scripts/backtestSmartMoney.ts` (ad hoc, no package.json entry — run via `pnpm --filter edgeboard-scripts exec tsx backtestSmartMoney.ts`): Brier-scores the smart-money-implied price against real resolutions, persisting a dedup'd, only-ever-grows history to `scripts/backtestSmartMoneyHistory.json` (reads `wallet_closed_positions`, independent of the `markets` table, so market-coverage changes don't affect its sample size). Several weighting variants were tried and rejected on this backtest before landing on the current formula — most recently, excluding early-sold positions from the average looked like a large improvement (v8) but mostly vanished under a live-plausible "open as of N days before resolution" reframing (v9), concluded to be substantially survivorship bias, not a real effect — **no code changed as a result.**

The waitlist route uses the **anon write client** (RLS allows INSERT, not SELECT). UI in `web/components/` (`LeaderboardTable`, `MarketsTable`, `TrendingPanel`, `RecentTradesFeed`, `WalletDossier`, `WalletActivity`, `WaitlistForm`, `OceanScene`).

### Access gate (removed)
Pre-launch waitlist gate **removed for public launch** — all routes open. (Historically bounced every route except `/early-access` + `/api/waitlist` unless the visitor held an `eb_access` cookie via `/unlock?key=<SITE_ACCESS_KEY>`. Re-add to `web/middleware.ts` for a closed beta.)

### Maintenance mode (`web/middleware.ts`, `MAINTENANCE_MODE` env var)
`web/middleware.ts` does three things: maintenance gate (first, short-circuits), Supabase auth session refresh, and the Signals page gate. When `MAINTENANCE_MODE` ∈ `on`/`1`/`true`/`yes` (case-insensitive, trimmed), it rewrites every **page** navigation to `/maintenance` and answers `503` with `Retry-After: 3600`. Matcher excludes `_next/`, `/api/`, `/maintenance`, static icons — **API routes keep serving.** Any other/unset value = normal. **It's a Vercel env var → a change needs a redeploy.** On: set `MAINTENANCE_MODE=on` (Production) → redeploy. Off: clear it → redeploy. All-or-nothing, immediate, no per-route variant. Screen = `web/app/maintenance/page.tsx`, styled by `.wm-page` / `.wm-*` in `globals.css` (wrapper is `.wm-page`, **not** `.wm` — a bare `.wm` collided with BrandMark's wordmark; see topnav-collision note below).

### Authentication & gated features (Supabase Auth + Google OAuth via `@supabase/ssr`)
Four signed-in-only surfaces: **Fresh Contacts** + **Convergence Zones** (home panels), **Signals** page (`/decision`), per-market **analytics** (`/market/[conditionId]`; the `/markets` listing stays public). Google OAuth only, no passwords, no new env vars (existing `NEXT_PUBLIC_SUPABASE_*`; Google secret lives in the **Supabase dashboard**). Pieces:
- `web/lib/supabaseBrowser.ts` — browser client (kept separate from `supabase.ts`, which imports `next/headers`) + `useUser()` hook (uses `getSession()`, local, for the UI gate; the real boundary is server-side).
- `web/components/`: `SignInButton`, `AuthNav`, `LockedPanel`. `web/app/signin/page.tsx` is the logged-out landing. `web/app/auth/callback/route.ts` exchanges the OAuth code for a session cookie (`exchangeCodeForSession`) and bounces to a same-site-only `next` (open-redirect guard).
- **Gate enforced server-side, not UI:** `getRequestUser()` (`supabase.ts`) validates the cookie with `getUser()`. The three gated API routes (`/api/fresh-entries`, `/api/crowded-markets`, `/api/decision-engine`) call it and return **401** when logged-out; they're `force-dynamic` with `Cache-Control: private, no-store`. `web/middleware.ts` refreshes the session cookie and redirects logged-out visitors off `GATED_PREFIXES` (`/decision`, `/market/` — trailing slash so `/markets` stays public) to `/signin`.
- **Why this preserves caching (the point):** home stays statically ISR-cached and no longer fetches gated data into its HTML; the two panels render `LockedPanel` for logged-out users and client-fetch from the auth-gated API only once signed in. `/decision` also stays cached, gated at the middleware door. DB load scales with signed-in pollers, not all traffic.
- **One-time dashboard setup (only place login can break — no RLS/schema changes):** (1) Google Cloud Console → OAuth client (Web), redirect URI = `https://eihgyehvtkvaohcytlyy.supabase.co/auth/v1/callback` (the **Supabase** callback); leave consent-screen logo + URLs blank (non-sensitive scopes need no branding verification); publish to Production. (2) Supabase → Auth → Providers → Google enabled with client ID + secret (*a typo'd ID/secret is the `Unable to exchange external code` error*); URL Config: Site URL `https://www.getwhalewatcher.me`, Redirect allowlist `…/auth/callback`, `http://localhost:3000/auth/callback`, `https://*.vercel.app/auth/callback`.

**Gate is application-level, not DB-level (deliberate; know the limit):** protected by the middleware redirect + the API routes' 401 — **not** Postgres RLS. Web reads every table with the **plain anon client** (no session) so pages stay ISR-cached, and **RLS is disabled on read tables**, so the anon key can read the "gated" cache tables directly via REST without signing in. Acceptable because all data derives from public Polymarket data — the gate is an engagement lever, not secret protection. **Do NOT "just enable RLS" on read tables** — every read uses the session-less anon client, so RLS without policies returns empty and **breaks the whole site.** A true hard gate needs RLS policies *plus* per-request session-aware reads passing the user's JWT (forfeiting ISR caching). Only go there for genuinely private/per-user data.

## Scoring lives in two files
- `scripts/config.ts` — **single source of truth** for every tunable (horizons, min trades/volume, recency gate `MIN_ACCOUNT_AGE_DAYS`, skill knobs `EDGE_SHRINKAGE_K`/`EDGE_FOR_TEN`/`SCORE_FLOOR`/`SCORE_MAX`, eligibility gates, bot heuristics, `ARBITRAGE_MIN_LEG_USD`, tiered recheck cooldowns `WALLET_RECHECK`, API pagination/retry, Gamma/CLOB hosts, `MARKETS_TOP_N`, price-history knobs, chip knobs `CHIP_BOARDS` + `PNL_BOARD_CHIP_TOP_N`). Change tuning here, not inline.
- `scripts/metrics.ts` — `computeMetrics` (per-horizon realized PnL, % return, win rate, forecasting edge, daily equity curve) and `computeSkillScore` (Bayesian-shrunk edge: 0 for zero/negative, else `[SCORE_FLOOR, SCORE_MAX]`; `null` for ineligible — too few trades, too little volume, or a sub-cent longshot). `EDGE_SHRINKAGE_K` is **50** (raised from 20) so a small high-edge sample can't pin a perfect score. **No dollar-based outlier flag** (removed) — it measured `largestWin / totalPnl` concentration, but `avgEdgePerShare` (what the score actually shrinks) is already per-position, not dollar-weighted, so the flag protected the wrong axis and could punish good conviction-sizing. **Recency gate:** `processWallet` nulls the score (and sets `ineligibleReason: "too_new"`) for any wallet whose history (earliest `/activity` fill via `earliestTradeMs`) spans < `MIN_ACCOUNT_AGE_DAYS` (14) — applied there, not in `computeSkillScore`, because the age signal comes from `/activity`. A null score keeps a brand-new account out of `leaderboard_cache` (which filters `skill_score is not null`). **`ineligibilityReason()`** is a sibling to `computeSkillScore` (same 3 gates, not folded in so `computeSkillScore`'s exact-constant tests stay untouched) returning *why* a wallet is ineligible (`insufficient_trades`/`insufficient_volume`/`longshot_entry`/`too_new`), persisted to `wallet_stats.ineligible_reason` and consumed by the tiered recheck cooldown (`walletRecheck.ts`, above). **`isScorableMarket`** excludes recurring "Up or Down" windowed markets (e.g. `Bitcoin Up or Down - May 31, 1:55PM-2:00PM ET`, matched by the `<time>-<time>` range in the title — a once-daily variant like `S&P 500 (SPX) Up or Down on March 2?` has no range and isn't affected) from every metric, applied as the first filter in `computeMetrics`. Investigated live: a top-3 wallet's wins showed up to 86 fills inside one 5-minute window and only a 43% win rate on last-10-second entries — spread-capture/market-making, not forecasting, and structurally impossible for a copy-trader to replicate. If a wallet's *entire* tracked history is windowed markets, filtering leaves it with `nTrades: 0` → `skillScore: null` → drops out of `leaderboard_cache` on the next rescore. **`excludeArbitrage`** strips positions in a conditionId flagged by `detectArbitrageConditions` (`botDetection.ts`, below) — position-level, not a wallet ban, same non-punitive shape as `isScorableMarket`.
- `scripts/specialty.ts` — `walletSpecialty` derives the category a wallet forecasts best (its chip). Reuses Skill Score edge math per category: `classifyMarket` (keyword on title → Politics/Crypto/Sports/Economy/Geopolitics/Culture, word-boundary, else "Other"), shrink each category's edge by `EDGE_SHRINKAGE_K`, chip the highest shrunk edge clearing `MIN_SPECIALTY_TRADES` and positive — else `null`. Also skips non-`isScorableMarket` positions (same carve-out, so windowed-market churn can't earn a Crypto chip either). Computed in `processWallet`, persisted to `wallets.specialty` in the same upsert. Keyword classifier is a `ponytail:` shortcut — upgrade path (a `condition_id`→Gamma-tag map cached during `ingest:markets`) noted in the file.

**Bot detection** (`scripts/botDetection.ts`): `botSignal()` flags on the first of four signals — trades/day (`MAX_TRADES_PER_DAY`), min-avg-trade-size (`MIN_AVG_TRADE_SIZE_USD`), simultaneous open markets (`MAX_SIMULTANEOUS_MARKETS`, raised 30→50 since some genuinely broad-forecasting wallets legitimately hold many markets at once), or **fast-flipper** (round-trips dominated by sub-`FAST_FLIP_MAX_HOURS` holds — `FAST_FLIP_FRACTION` of ≥`FAST_FLIP_MIN_ROUNDTRIPS`). Fast-flipper excludes non-copyable arb/hedge/scalp churn (e.g. BTC 15-min markets) *from being flagged as a bot* — it isn't a scoring exclusion by itself. The actual scoring exclusion for that same churn is `isScorableMarket` (`metrics.ts`, above): Skill Score measures *copyable* forecasting edge, so legit human scalpers are out of scope too. Holding time derived from `/activity` fills already pulled. Tune from the per-signal breakdown log (`Bot breakdown: trade_rate=… dust_trades=… simultaneous_markets=… fast_flipper=…`). **`detectArbitrageConditions`** is a separate, sibling function (same file, not folded into `botSignal` — its output is a per-market exclusion set for `excludeArbitrage`, not a wallet-level bot flag): flags conditionIds where a wallet held *both* outcome legs concurrently, each leg's cost basis clearing `ARBITRAGE_MIN_LEG_USD` ($10, dust floor). Detected from the raw chronological `/activity` stream specifically so a genuine changed-mind reversal (sell YES, later buy NO — no overlap) isn't flagged, only real concurrent holds are; the aggregated `ClosedPosition` records `computeMetrics` sees don't preserve enough chronology to tell the two apart. Verified live: caught a wallet holding a $561 YES position concurrently with a separate $112 NO round-trip on the same match.

## Critical conventions and gotchas

- **The Supabase `Database` type is hand-maintained in two copies; no codegen.** Inline in `scripts/ingest.ts` and again in `web/lib/types.ts`. Each is a subset of the migrations typing only that workspace's tables — `scripts` has `market_price_history`/`market_price_meta`, omits `waitlist`; `web` has `waitlist` + `market_price_history` (read for the Convergence overlay), omits `market_price_meta`. Divergence is expected. For columns the code selects, `strict` + `noUncheckedIndexedAccess` make `pnpm typecheck` catch drift; for newly-added columns nothing references yet, update by hand.
- **`scripts/` is ESM (`NodeNext`); relative imports use `.js` extensions** (`import { CONFIG } from "./config.js"` resolves to `config.ts`). Keep the `.js` suffix or tsx/tsc fail. `web/` uses Bundler resolution + the `@/*` alias — don't mix styles.
- **Two TS configs, both `strict` + `noUncheckedIndexedAccess` + `exactOptionalPropertyTypes`** — optional props and indexed access need care.
- **Env vars** (copy `.env.example` → `.env.local`; root covers scripts, `web/.env.example` covers web):
  - web (browser-safe): `NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`.
  - scripts (writes): also `SUPABASE_SERVICE_ROLE_KEY`; optional `POLYMARKET_API_BASE`. `ingest.ts` loads `../.env.local` then local `.env.local`.
  - **Keep the service-role key out of the web app** — the read path uses anon only.
- Polymarket API field names are inconsistent; `polymarket.ts` maps defensively via `readString`/`readNumber` with fallback key lists. On a schema shift, **extend the key arrays**, don't assume one field name.
- **Resolved-but-unredeemed P/L correction (`mapClosedPosition`).** Polymarket reports `realizedPnl: 0` for a position held to resolution but not yet redeemed (settled, `curPrice` 0/1, winnings unclaimed). Recording 0 understated win rate + showed blank P/L. So when the outcome is known and reported P/L is exactly 0, `mapClosedPosition` substitutes the settlement value `size·(outcome − avgPrice)`. A partially-sold position reports non-zero P/L, so only the fully-held case is corrected. `polymarketLive.ts` applies the same for non-board wallets.
- **Outcome label + event on trades.** `wallet_trades` / `wallet_closed_positions` carry `outcome_label` (real "Over"/"Under"/team/"Yes"/"No") + `event_slug` (023), captured in `mapActivity`/`mapClosedPosition`. Trade history shows the real label + a humanized event subtitle, so grouped sports markets whose title omits the event (e.g. CS2 "Games Total: O/U 2.5") are legible.
- Addresses are lowercase everywhere (ingestion, API routes, lib). Preserve this in new lookups.
- **Polymarket rate limits** ([docs](https://docs.polymarket.com/api-reference/rate-limits)). Three hosts, each its own Cloudflare bucket over sliding 10s windows (queued, not hard-rejected): Data API (`data-api.polymarket.com`), Gamma (`gamma-api.polymarket.com`), CLOB (`clob.polymarket.com`). Per-endpoint: `/closed-positions` + `/positions` = **150/10s** (binding); `/trades` = **200/10s**; `/activity`/`/value`/`/v1/leaderboard` fall under Data API general **1,000/10s**; CLOB `/prices-history` under CLOB general **9,000/10s**. `polymarket.ts` runs **one serial rate gate per lane** (`throttle(lane)`), keyed by `CONFIG.REQUEST_INTERVAL_MS`: `restricted` (closed-positions/positions, 90ms ≈111/10s), `general` (rest of Data API + Gamma `/events`, 30ms ≈333/10s), `clob` (prices-history, 10ms ≈1,000/10s). When tuning down, keep each lane under cap — `restricted` ≥67ms, `general` ≥50ms. `fetchJson` honors `Retry-After` before exponential backoff.

## Local dev & deployment gotchas

**The web app and the ingest pipeline deploy to two different places from the same `master` branch, and only one is automatic.**

- **Branch-per-feature workflow.** Implement a feature → **push to a new branch** (not `master`) so the user can open a Vercel **preview**. **Don't merge to `master` yourself** — `master` is Production. Only when the user says to merge: merge into `master`, push, **then delete the feature branch** (local `git branch -d` + remote `git push origin --delete <branch>`). **No PRs.** Commit-message convention: concise subject, optional body, trailing footer `Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>`. (Bash-tool gotcha: don't use PowerShell `@'…'@` here-strings with `git commit -m` in the Bash tool — Git Bash prepends a stray `@`; use repeated `-m` flags or a real heredoc.)
- **Don't run `pnpm build`/`pnpm start` while `pnpm dev` is running.** They share `web/.next`; a production build against a dir `next dev` is using corrupts it (symptom: unstyled/broken localhost). Stop dev first, or delete `web/.next`.
- **Global CSS class-name collisions are silent and bite on deploy.** `globals.css` is one flat global stylesheet (no Modules), so a reused class name has the later/more-specific rule bleed onto both. `.wm` (maintenance wrapper) collided with BrandMark's topnav wordmark `<div class="wm">`: the maintenance rule (`position:fixed; inset:0; z-index:100`) hijacked the wordmark into a full-screen overlay covering the nav links. Fixed by renaming to `.wm-page`. **Diagnose in-browser:** if an element is in the DOM but not visible, `document.elementFromPoint(cx, cy)` at its center returns the covering element's class. New component → prefer a scoped/prefixed class over a bare generic one; grep `globals.css` for the name first.
- **Web app → Vercel, auto-deploys from GitHub `master`.** Pushing `master` triggers Production (branch pushes = Previews); Vercel Root Directory is `web/`. Env-var changes take effect only on a *new* build — redeploy. Service-role key is intentionally **not** on Vercel.
  - *Rollback gotcha:* a Vercel **Instant Rollback** pins the domain to one deployment and stops new pushes auto-promoting (symptom: domain serves old build after a push). Fix: Deployments → newest `master` → ⋯ → **Promote to Production**.
  - *Statically-prerendered API route gotcha (ROOT CAUSE, seen in prod):* a **no-argument `GET` handler that reads no request data is statically prerendered at build time** — Next runs it **once during `next build`**, bakes that JSON snapshot in, and serves it unchanged until the next deploy. The `Cache-Control: s-maxage=…` header only controls the CDN; it can't un-freeze a build-time body. Hit `/api/recent-trades` + `/api/crowded-markets`: the feed froze at deploy, its newest trade aged indefinitely while the backend was healthy. A redeploy only re-freezes immediately (freeze age = time since deploy). **Tells:** stale "Nh ago" = `elapsedFrom(latestTradedAt)` (age of newest baked-in trade); `curl -sD - …/api/recent-trades -o /dev/null` shows `Age` ≈ time-since-deploy with `X-Vercel-Cache: HIT` only climbing; `pnpm build` lists the route `○ (Static)` not `ƒ (Dynamic)`. (Home page ISR `revalidate=600` keeps refreshing — distinguishes from a rollback.) **Fix (permanent):** add `export const dynamic = "force-dynamic";` so Next renders on demand; the existing `s-maxage` header still CDN-caches, so no per-request DB load. Confirm with `pnpm build` showing `ƒ`.
- **Ingest pipeline (`scripts/`) → Heroku `edgeboard-ingest`, NO auto-deploy.** It runs the last `git push heroku master`'d slug, so pushing GitHub master does **not** update it. **After any change under `scripts/`, run `git push heroku master`** or the scheduled jobs run stale code. (Real bug: a markets fix was live on Vercel but unpushed to Heroku for 13 commits, so scheduled `ingest:markets` kept overwriting with old logic.) Check deployed commit: `git fetch heroku && git rev-parse --short heroku/master`; env via `heroku config -a edgeboard-ingest`.
- **How scheduled jobs fire (two mechanisms).** Frequent partials run through an always-on **webhook server** (`scripts/server.ts`, the Heroku `web` dyno, `pnpm webhook`) that **cron-job.org** POSTs to on a schedule (pinging every minute keeps the dyno awake). Each route spawns the matching partial and is single-flight (a 2nd ping → `409 Already running`):
  - `POST /refresh/feed` → `pnpm ingest:feed` (~10 min)
  - `POST /refresh/markets` → `pnpm ingest:markets` (~hourly)
  - `POST /refresh/rescore` → `pnpm ingest:rescore` (hourly)
  
  All need `Authorization: Bearer $CRON_SECRET` (`heroku config:set CRON_SECRET=… -a edgeboard-ingest`); wrong → `401`, unknown path → `404`, accepted → `202`. URL: `https://edgeboard-ingest-ac4c7fff0498.herokuapp.com`. This webhook pattern (vs a Heroku Scheduler one-off dyno) is deliberate — hourly/10-min jobs reuse the running web dyno instead of burning dyno hours. Only the **daily full `pnpm ingest`** runs as a Scheduler one-off. **Change feed/markets/rescore cadence in cron-job.org (not Heroku Scheduler); a new partial = a `/refresh/<mode>` route + a cron-job.org job.**
- **Full `pnpm ingest` runs once daily via Heroku Scheduler, and `FULL_INGEST_EVERY_HOURS` is deliberately `0` (gate disabled).** The gate exists in `main()` for a Scheduler trigger *more frequent* than the desired cadence (`main()` no-ops with `Skipping full ingest: UTC hour N is not a multiple of M` unless the UTC hour is a multiple of the env var — e.g. `4` would mean 00/04/08/12/16/20 UTC) — its original purpose, since Heroku Scheduler can't express "every N hours" directly, only a fixed frequency. Since the Scheduler job itself is configured to fire once/day, the gate is redundant and left at `0` (unset also disables it). **Verified live (2026-07-02):** candidate discovery — a full-ingest-only step, so its timestamps are a reliable tell — fired exactly once in a 24h window (00:00 UTC), with zero new candidates found in any other hour, confirming no hourly/duplicate full-ingest runs are happening. If Scheduler's frequency is ever changed to hourly again, set `FULL_INGEST_EVERY_HOURS` back to a divisor (e.g. `4`) to restore the throttle. **Force a full ingest right now regardless of gate state:** `heroku run:detached "FULL_INGEST_EVERY_HOURS=0 pnpm ingest" -a edgeboard-ingest` (an inline override like this doesn't touch the persistent config var — don't confuse the two). Partials aren't gated.
- **The daily full ingest runs on a 512 MB dyno and is memory-bound.** Heroku **Eco and Basic are both 512 MB** (Basic adds no memory; only Standard-2X = 1 GB does). The full ingest *discovers* ~5k wallets, though the tiered recheck cooldown (above) now actually re-fetches far fewer of them once warmed up. Heroku signals **R14** (over 512 MB — only throttles/swaps, survives) and **R15** (~2×/~1 GB — `SIGKILL`, exit 137); respect the R15 line. Two things keep it under: **board-scoping in step 8** (peak ∝ `TOP_N`) and write-once buffer frees (`collected*.length = 0`) before the tail. Bitten twice — an OOM kill mid-tail and a `HeadersOverflowError` from an under-chunked `.in()` (see chunking rule below). When adding to the tail, prefer streaming/paged reads over loading a whole table.

## Supabase load & the "overloaded DB" recovery playbook

Supabase is on a **small free tier** with two easy-to-blow limits: a **compute ceiling** (hit 100% CPU / high mem / high disk-IO under write churn + per-request full-table scans) and a **5 GB/month egress budget** (overage → project restricted). Both driven by the same anti-pattern — **reading more rows, more often, than a request needs.** Production root causes + fixes:

- **Per-request full-table scans (fixed).** Old `getCrowdedMarkets` scanned all of `wallet_positions` per render → now precomputed into `crowded_markets_cache`. Any new read path scanning a whole table per request — or a page dropping ISR for `force-dynamic` — re-introduces this; precompute into a cache table instead.
- **Egress blowout from over-fetching (fixed).** Exceeded 5 GB (6.85 GB). Cause: `getRecentLeaderboardTrades` downloaded the *entire* position cache (thousands of rows) to derive cost-basis for ≤200 trades, and clients poll `/api/recent-trades` every 60s while the edge cache held only 60s → ~once/minute all day. Fix: (1) **lengthen cache windows to data cadence** — recent-trades `s-maxage` 60→600, markets 60→300, home `revalidate` 300→600; (2) **scope the read to what's shown** — basis lookups now filter to the feed's `condition_id`s, chunked 60 ids/request.
- **Job churn / misconfiguration (the real incident).** The cron-job.org **feed** job was set to **every 1 minute** (not ~10), *and* a duplicate `ingest:feed` existed in **Heroku Scheduler** — two sources spawned overlapping feed runs that crash-looped and pinned the instance. **Keep feed ≥10 min, from exactly one source (cron-job.org), never duplicated in Heroku Scheduler.** Wipe-and-replace tables (`recent_trades` + `wallet_trades` + `wallet_positions`, rewritten every feed run) generate dead-tuple bloat ∝ job frequency.
- **Reclaiming disk bloat.** `VACUUM FULL` **cannot run through the SQL editor** (rewrites the whole table, exceeds the gateway timeout; the timeout does *not* stop the VACUUM — Postgres keeps running it holding `ACCESS EXCLUSIVE`). For wipe-and-replace **cache** tables, `TRUNCATE` instead (instant; next ingest refills). `supabase/maintenance/reclaim_bloat.sql` lists churned tables. **Do NOT truncate `market_price_history`/`market_price_meta`** (append-only + immutable; forces an expensive full CLOB re-fetch), **`wallets`**, or **`candidate_wallets`** (accumulated lifecycle state). After a TRUNCATE, run a full ingest (also repopulates `crowded_markets_cache`).
- **When the DB is wedged** (even a trivial SQL-editor query returns `Connection terminated due to connection timeout`): that's lock/connection-pool exhaustion — usually an orphaned `VACUUM FULL` still running plus zombie connections from crash-looping jobs. Recovery, in order: (1) stop writers — `heroku ps:scale web=0 -a edgeboard-ingest` + **pause Heroku Scheduler jobs**; confirm with `heroku ps -a edgeboard-ingest`; (2) **restart the Supabase project** (Settings → General → Restart) to clear stuck queries + free the pool; (3) run pending migration + `TRUNCATE` while quiet; (4) force a full ingest; (5) re-scale `heroku ps:scale web=1` + re-enable the (single, ≥10-min) jobs once healthy.

### Design rules for any new read path or feature
The tier is small on **both** compute and egress — treat the DB as scarce on every feature. Before adding a query/page/route:
1. **Never scan a whole table per request.** Constrain reads with `.eq()`/`.in()` on an indexed column scoped to what renders. If a feature needs a board-wide aggregate, **precompute into a cache table during ingest** (the `crowded_markets_cache` pattern).
2. **Select only the columns you use.** No `select("*")` on wide/high-row tables (every extra column is egress on every row of every request).
3. **Fetch only the rows the response shows.** Derive the key set from the primary result and `.in(...)` on *those* keys. Chunk large `.in()` lists **by value length** to stay under PostgREST's ~16 KB request-URL limit — overflow throws `HeadersOverflowError` (`UND_ERR_HEADERS_OVERFLOW`), aborting the run. Ingest sizes per id type: `LEADERBOARD_FILTER_CHUNK` (200) for 42-char addresses, `ASSET_FILTER_CHUNK` (100) for ~77-char CLOB token ids.
4. **Cache at a window matching how often the data changes.** Data refreshes on the ingest cadence (feed ~10 min, markets/rescore ~hourly, full daily); set API `s-maxage` + page `revalidate` to that. **Never use `force-dynamic`/`no-store` on a Supabase-backed page** unless it's truly per-user.
5. **Mind client polling × cache window.** Components poll their `/api/*` route every 60s (`POLL_INTERVAL_MS`); the edge cache collapses concurrent pollers into one origin read per `s-maxage` window, so the *cache window*, not the poll interval, sets DB load.
6. **Writes: prefer upsert/wipe-and-replace on cache tables over high-frequency churn.** Every rewritten row is dead-tuple bloat ∝ job frequency; keep partial-refresh cadence at documented intervals.

When in doubt: *"Does this read scale with rows-shown, or table-size? And how often does it really need to re-run?"* If "table-size" or "every request," redesign before shipping.
